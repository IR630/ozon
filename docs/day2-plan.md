## Тема дня и рамка

День 2 — **узлы контура по отдельности**: каждый узел работает standalone на моках.
Сквозная интеграция — день 3 (`v0.1-skeleton`), не сегодня. Держим overfit-single-batch:
P1–P4 работают на **одном** товаре (Короб 300); все 11 трогает только P5 (устойчивость
на ленте, не классификация).

Ограничение среды (честность): Gazebo запускается только в WSL `ozon` / Docker с
`LIBGL_ALWAYS_SOFTWARE=1`. Sim-задачи (P2, P5) проверяются скриптами в WSL; чистая
Python-логика (измерения P3, классификатор-нода P4, тайминг упреждения P1) — pytest.

## Поток данных, собираемый в дне 2

```
gz camera ──bridge──▶ /camera/image, /camera/depth_image, /camera/camera_info
   │
   ▼  P3 perception_node: сегментация + габариты(мм) + K + позиция
   ├─▶ /item/measurement    ── контракт ItemMeasurement (новый, см. ниже)
   │
   ▼  P4 classifier_node: classify(dims,k) + confidence + консерв. политика
   ├─▶ /item/classification ── контракт ItemClassification (существующий)
   │
   ▼  P1 controller: position-tracking + упреждение по скорости ленты
   ├─▶ /pusher/cmd
   │
   ▼  P2 pusher: призматическая лопатка сталкивает товар с ленты → зона C
```

## Решение по контракту: новый `ItemMeasurement.msg`

Перцепция меряет `dims+K`, но `category`/`confidence`-политику присваивает
классификатор — это его зона ответственности. Переиспользование `ItemClassification`
с пустой `category` размывает владение полем, что против «явных контрактов данных»
(CLAUDE.md). Поэтому вводим отдельный тип `ros_msgs/msg/ItemMeasurement.msg`:

```
std_msgs/Header header        # stamp = момент измерения, frame_id = камера
uint32 item_id                # tracking id, уникален в пределах прогона
float32[3] dims_mm            # габариты по убыванию, миллиметры
float32 k                     # r_inscribed / R_circumscribed, [0..1]
float32 confidence            # уверенность измерения [0..1]
geometry_msgs/Point position  # позиция товара, метры, world frame
```

`category` здесь НЕТ — это выход классификатора. PR в `ros_msgs/` (владелец P1),
запись в `decisions.md`. Разблокирует P3 и P4 независимо друг от друга.

## Задачи по потокам

### P4 — classifier_node (rclpy-нода, тест в WSL/ROS)
- **Делаем:** `src/classifier_node.py` — подписка `/item/measurement`, вызов
  `classify()` из `src/classification.py`, `confidence` проброшена из измерения
  без изменений, публикация `/item/classification`. Тонкая обёртка: логика правил
  живёт в `classify()` (единственный источник), нода лишь кладёт результат на шину.
- **Проверка:** node-level pytest на rclpy — probe-нода публикует мок-измерение
  Короба → assert `category == "B"` и заполненный `ItemClassification`. Тест под
  `importorskip("rclpy")`: на pytest-джобе CI (голый ubuntu, без ROS) и на
  Windows-хосте пропускается, реально гоняется в WSL (colcon build ros_msgs +
  source). Зелёный тест = критерий готовности.
- **НЕ делаем:** реальную перцепцию, интеграцию с gz, политику неуверенности
  (K у порога, габариты у границ → C/D) — это **день 4**.

### P3 — perception (проверяется на depth-PNG, без WSL) ✅
- **Делаем (факт):** `src/perception.py` — единое ядро `measure_item()`: сегментация
  по depth (`depth < depth_ленты − ε`), габариты (bbox → мм через intrinsics),
  **K** (вписанная/описанная окружность выпуклой оболочки маски — то же определение,
  что в анализе `models.md`), **позиция в world** (центроид маски; отображение
  пиксель→мир проверено эмпирически кадром со смещённым коробом: (1.791, 0.100)
  против истины (1.8, 0.1)), **отсечка частично видимых** (маска у края кадра →
  None, ждём следующий кадр 15 Гц). Оверлей bbox+числа+K в `docs/report/img/`.
- **Проверка (факт):** синтетика с аналитикой (квадрат K=1/√2, прямоугольник
  K=0.554, круг K>0.97, позиция до 1e-6) + два реальных кадра: центр — габариты
  ±10 мм, K=0.56, позиция ±2 мм; смещённый — позиция ±10 мм, габариты ±20 мм.
- **Ограничение v0:** внеосевой ракурс подмешивает боковые грани в маску →
  габариты завышаются до ~15–20 мм; учесть у порогов классификации (день 4).
- **НЕ делаем:** устойчивость к ориентациям (день 4–5), остальные 10 товаров.

### P2 — pusher v0 (WSL-runtime) ✅
- **Делаем:** лопатка на призматическом джойнте у −Y края ленты (толкает в +Y),
  JointController на топике `/pusher/cmd`, **inline в `cell.sdf`** на x=2.5 (как
  конвейер/камера/зоны — не отдельный `model://`, чтобы не плодить дубли и не
  ломать `check_sdf`). Скрипт `scripts/smoke_pusher.sh` по образцу `smoke_belt.sh`.
- **Проверка (факт):** `ign topic -t /pusher/cmd` (1.2 м/с) → Короб уходит с ленты
  на C-сторону: y 0.12 → **0.69** (край ленты 0.25). PASS.
- **Замечание:** ручной тест **механизма**. Истинная категория Короба 300 = **B**
  (габариты в норме, K≈0.71 < 0.8); зона C здесь — только «лопатка сталкивает вбок».
- **Ограничение v0:** одинарная лопатка теряет контакт, когда короб падает с края
  ленты (0.4 м) на пол → доезжает до ~0.69, а не до патча C (центр y=1.2). Точная
  доставка на кейдж C — день 3 (придвинуть кейдж / жёлоб).
- **НЕ делаем:** зону D / реверс / выбор реального механизма (день 5).

### P1 — launch + упреждение (тайминг тестируется без WSL, launch — в WSL) ✅
- **Делаем (факт):** `launch/skeleton.launch.py` — bridge (`sim/bridge.yaml`) +
  `perception` + `classifier` одной командой. `src/` — не ROS-пакет, поэтому ноды
  гонятся `python3 -m src.<node>` (cwd=корень, overlay `ros_msgs`). Упреждение —
  чистая функция `src/tracking.py`: `fire_time = t0 + (x_push − x_cam)/v − latency`,
  v из констант.
- **Проверка (факт):** живой прогон в WSL — Gazebo + спавн Короба 300 + launch →
  `/item/measurement` (296×200×198 мм, K=0.56, позиция (1.501, 0.001), stamp кадра)
  → `/item/classification` **category B**. Цепочка камера→классификация работает
  end-to-end; `tests/test_perception_node.py`, `tests/test_classifier_node.py`,
  `tests/test_tracking.py` зелёные.
- **НЕ делаем:** controller_node (classification→pusher) и маршрутизацию — день 3.

### P5 — устойчивость 11 SDF (WSL-runtime) ✅ 10/11
- **Делаем:** `scripts/check_stability.sh` — цикл по 11 товарам: спавн, отстой на
  статичной ленте, **мягкий пуск** (рамп 8 шагов до скорости из констант), проверка
  «едет с лентой (dx>1.0), не проваливается и не улетает (0.35≤z≤1.0)». Мир
  рестартится на каждый товар; лента прекатывается в −3.2 → ход 6.4 м на эпизод.
- **Результат (факт):** **10/11 стабильны**. Мгновенный старт 0→1 м/с подбрасывал
  круглые (8/11); диагностика траекторий → мягкий пуск вылечил Бутылку и Пуфик.
  FAIL только Шлем: выпуклая оболочка — «качалка» (обод неплоский), укатывается
  детерминированно; перебраны рамп/kp-kd/шаг физики/переворот — не лечится
  параметрами, только геометрией удержания (день 3). Бортики НЕ добавляем — сплошной
  борт ломает depth-камеру и боковой толкатель (`docs/decisions.md`).
- **Следствие для дня 3:** контроллер обязан командовать ленту рампом (записано
  в decisions.md и в шапке `cell.sdf`).
- **НЕ делаем:** классификацию/маршрутизацию этих товаров (день 4); выбор геометрии
  удержания (день 3).
