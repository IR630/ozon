## 2. БЛОКЕР: ОС не тянет ни Docker, ни WSL2

Это главная проблема, и она не чинится настройкой проекта.

Установлено фактами с машины:

- Windows 10 **LTSC 2019, build 17763** (версия 1809).
- `docker` — не установлен, каталога `C:\Program Files\Docker` нет.
- `wsl` — команды нет вообще.
- Hyper-V — не включён.
- Запрос состояния компонентов Windows вернул `The requested operation requires
  elevation` → **прав администратора на машине нет**.

Почему это упирается в потолок:

- **WSL2 требует build 18362 (версия 1903) и выше.** LTSC 2019 зафиксирован на
  17763 и до 1903 не обновляется в принципе — это отдельная редакция с 10-летним
  циклом, а не отставшая сборка. То есть `wsl --import ... --version 2` и
  `systemd=true` из README здесь неисполнимы никакими правами.
- **Актуальный Docker Desktop требует Windows 10 21H2/22H2 и новее** — 17763
  ниже минимума. Теоретически остаётся легаси-путь: Docker Desktop 2.x на
  Hyper-V-бэкенде (редакция Enterprise это позволяет), но это снятая с поддержки
  версия, и включение Hyper-V всё равно требует администратора.

**Следствие:** команда `bash scripts/check_clean_deploy.sh` — та самая «проверка
развёртывания одной командой» — на этой машине не запускается: скрипт первым
делом делает `command -v docker` и выходит с `ABORT: docker is required`.

### Что из-за этого осталось непроверенным

## 4. Git: два дефекта конфигурации, оба блокируют обмен кодом

**4.1. `git fetch` и `git push` виснут намертво.** Первая же попытка
`git fetch --all` не завершилась за 2 минуты и была убита по таймауту.
При `GIT_TERMINAL_PROMPT=0` диагноз виден явно:

```
fatal: User cancelled dialog.
fatal: could not read Username for 'https://github.com': terminal prompts disabled
```

Причина именно такая: credential helper **настроен** (`credential.helper=manager`,
и `git-credential-manager.exe` на месте в составе Git for Windows) — но
сохранённых учётных данных для `github.com` нет. GCM пытается открыть
графический диалог логина, а в неинтерактивной сессии этот диалог не появляется.
Поэтому любая сетевая операция git либо ждёт вечно, либо отваливается.

Лечится однократным интерактивным входом: выполнить `git push` (или
`git fetch`) руками из обычного терминала и пройти авторизацию в открывшемся
окне GCM. После этого учётка ложится в Windows Credential Manager и всё
последующее работает без вопросов.

Сеть при этом полностью рабочая — `pypi.org` и `github.com` отдают 200, пакеты
скачались. Дело только в учётных данных.

Это важно для правила из `CLAUDE.md` «проверку начинать с `git pull`»: на
неподготовленной машине `git pull` не падает с ошибкой, а зависает, и это легко
принять за медленную сеть.

**4.2. Ремоут `true` не настроен.** `GIT.md` требует пушить в оба репозитория и
описывает ремоут `true` с двумя push-URL (organizers `hackathonsrus/...` +
`IR630/ozon`). На этой машине в `.git/config` есть только:

```
[remote "origin"] url = https://github.com/IR630/ozon.git
```

То есть отправить что-либо организаторам отсюда нельзя, а требование «истории
обязаны совпадать» не выполнимо и даже не проверяемо. Нужны команды из GIT.md:

```
git remote add true https://github.com/hackathonsrus/ozone-tech_ii_v_massy_883.git
git remote set-url --push true https://github.com/hackathonsrus/ozone-tech_ii_v_massy_883.git
git remote set-url --add --push true https://github.com/IR630/ozon.git
```

**4.3. `user.name` / `user.email` не заданы.** Первый же `git commit` упал с
`Author identity unknown ... unable to auto-detect email address (got
'Ivan@PC5.(none)')`. Прописано локально для этого репозитория:

```
git config user.name "Alex Bessonov"
git config user.email "alexbessonov278@gmail.com"
```

Если машина будет использоваться дальше — имеет смысл сделать это через
`--global`, иначе то же самое всплывёт в следующем checkout.

**4.4. Мелочь: `git` не виден из PowerShell.** Бинарь есть (`C:\Program Files\Git`,
version 2.45.1), но в `PATH` PowerShell его нет — доступен только внутри Git Bash.
README в разделе про WSL даёт `git worktree add ...` именно как PowerShell-команду,
и она здесь не выполнится. Лечится дописыванием `C:\Program Files\Git\cmd` в PATH.

## 6. Риск: `requirements.txt` без пинов — сегодня повезло

Установка 02.08 разрешилась в:

```
numpy 2.5.1   scipy 1.18.0   trimesh 5.0.0
opencv-python-headless 5.0.0.93   pytest 9.1.1   ruff 0.16.1
```

Это **ровно те два релиза, которые по CLAUDE.md уже дважды роняли CI** — `ruff
0.16` (28.07) и `trimesh 5.0.0` (01.08). Сейчас оба прошли: набор правил ruff
теперь прибит в `pyproject.toml` (`select = ["E4","E7","E9","F"]`), а trimesh
5.0.0 конфликтовал с numpy 1.x, которого здесь нет — приехал numpy 2.5.1.

То есть защита сработала, но результат Python-развёртывания всё равно зависит от
даты установки: `requirements.txt` не пинует ничего. `docker/pip-constraints.txt`
эту дыру не закрывает — он намеренно описывает только образ (там `numpy==1.21.5`,
который на Windows и Python 3.14 просто не соберётся).

Это осознанное решение (комментарий в `pip-constraints.txt` объясняет, зачем
`requirements.txt` оставлен свободным), поэтому предлагаю не менять на ходу, а
просто знать: «у меня Python-часть зелёная» и «у тебя Python-часть зелёная» —
это не обязательно одинаковые наборы версий.
