## 2. БЛОКЕР: ОС не тянет ни Docker, ни WSL2

Это главная проблема, и она не чинится настройкой проекта.

Установлено фактами с машины:

- Windows 10 **LTSC 2019, build 17763** (версия 1809).
- `docker` — не установлен, каталога `C:\Program Files\Docker` нет.
- `wsl` — команды нет вообще.
- Hyper-V — не включён.
- Запрос состояния компонентов Windows вернул `The requested operation requires
  elevation` → **прав администратора на машине нет**.

Почему это упирается в потолок:

- **WSL2 требует build 18362 (версия 1903) и выше.** LTSC 2019 зафиксирован на
  17763 и до 1903 не обновляется в принципе — это отдельная редакция с 10-летним
  циклом, а не отставшая сборка. То есть `wsl --import ... --version 2` и
  `systemd=true` из README здесь неисполнимы никакими правами.
- **Актуальный Docker Desktop требует Windows 10 21H2/22H2 и новее** — 17763
  ниже минимума. Теоретически остаётся легаси-путь: Docker Desktop 2.x на
  Hyper-V-бэкенде (редакция Enterprise это позволяет), но это снятая с поддержки
  версия, и включение Hyper-V всё равно требует администратора.

**Следствие:** команда `bash scripts/check_clean_deploy.sh` — та самая «проверка
развёртывания одной командой» — на этой машине не запускается: скрипт первым
делом делает `command -v docker` и выходит с `ABORT: docker is required`.

## 4. Git: два дефекта конфигурации, оба блокируют обмен кодом

**4.1. `git fetch` и `git push` виснут намертво.** Первая же попытка
`git fetch --all` не завершилась за 2 минуты и была убита по таймауту.
При `GIT_TERMINAL_PROMPT=0` диагноз виден явно:

```
fatal: User cancelled dialog.
fatal: could not read Username for 'https://github.com': terminal prompts disabled
```

Причина: credential helper **настроен** (`credential.helper=manager` из
системного `C:/Program Files/Git/etc/gitconfig`, `git-credential-manager.exe` на
месте) — но на момент проверки сохранённой учётки для `github.com` ещё не было.
GCM пытался открыть графический диалог логина, а в неинтерактивной сессии этот
диалог показать некому, и он отменял сам себя.

Сеть при этом полностью рабочая — `pypi.org` и `github.com` отдают 200, пакеты
скачались. Дело было только в учётных данных.

**Закрыто 02.08 и проверено.** После однократного интерактивного входа GCM
положил учётку в Windows Credential Manager, причём постоянно:

```
Target: LegacyGeneric:target=git:https://github.com
User:   Ivana-banana
Local machine persistence
```

Ключ заведён на **хост**, а не на конкретный репозиторий (`useHttpPath` для
github не включён), поэтому одна запись покрывает и `origin`, и `true` — оба
живут на `github.com`. Повторный вход не требуется.

Проверено прямым прогоном из неинтерактивной сессии, без единого запроса пароля:
`git push true main` (ушёл в оба репозитория), `git ls-remote true main`,
`git ls-remote origin main`, `git fetch --all` — все `exit=0`.

Оговорка для того, кто будет это читать: пока учётки не было, `git pull` здесь
не падал с ошибкой, а **зависал** — это легко принять за медленную сеть. Правило
`CLAUDE.md` «проверку начинать с `git pull`» на неподготовленной машине выглядит
именно так.

**4.2. Ремоут `true` не настроен.** `GIT.md` требует пушить в оба репозитория и
описывает ремоут `true` с двумя push-URL (organizers `hackathonsrus/...` +
`IR630/ozon`). На этой машине в `.git/config` есть только:

```
[remote "origin"] url = https://github.com/IR630/ozon.git
```

То есть отправить что-либо организаторам отсюда было нельзя, а требование
«истории обязаны совпадать» не выполнимо и даже не проверяемо.

**Исправлено 02.08.** Ремоут добавлен по GIT.md, с двумя push-URL — обычный
`git push true main` теперь уходит сразу в оба репозитория:

```
git remote add true https://github.com/hackathonsrus/ozone-tech_ii_v_massy_883.git
git remote set-url --push true https://github.com/hackathonsrus/ozone-tech_ii_v_massy_883.git
git remote set-url --add --push true https://github.com/IR630/ozon.git
```

Итоговая конфигурация:

```
origin  https://github.com/IR630/ozon.git                                  (fetch)
origin  https://github.com/IR630/ozon.git                                  (push)
true    https://github.com/hackathonsrus/ozone-tech_ii_v_massy_883.git     (fetch)
true    https://github.com/hackathonsrus/ozone-tech_ii_v_massy_883.git     (push)
true    https://github.com/IR630/ozon.git                                  (push)
```

**Сверка выполнена.** Оба репозитория указывают на один коммит:

```
514904fc040d88a4435b230e21f07f41e43386f9   refs/heads/main   (true)
514904fc040d88a4435b230e21f07f41e43386f9   refs/heads/main   (origin)
```

Попутно выяснилось, что репозиторий организаторов **отставал на 4 коммита**
(`c369232..514904f`) — их и дослали обычным fast-forward, без `--force`, как и
предписывает GIT.md. Это ровно тот случай «пушнули из ветки с неполной
настройкой», от которого GIT.md и страхует: пока ремоута `true` не было,
push уходил только в зеркало.

**4.3. `user.name` / `user.email` не заданы.** Первый же `git commit` упал с
`Author identity unknown ... unable to auto-detect email address (got
'Ivan@PC5.(none)')`. Прописано локально для этого репозитория:

```
git config user.name "Alex Bessonov"
git config user.email "alexbessonov278@gmail.com"
```

Если машина будет использоваться дальше — имеет смысл сделать это через
`--global`, иначе то же самое всплывёт в следующем checkout.

**4.4. Мелочь: `git` не виден из PowerShell.** Бинарь есть (`C:\Program Files\Git`,
version 2.45.1), но в `PATH` PowerShell его нет — доступен только внутри Git Bash.
README в разделе про WSL даёт `git worktree add ...` именно как PowerShell-команду,
и она здесь не выполнится. Лечится дописыванием `C:\Program Files\Git\cmd` в PATH.

### Итерация 3 — `--python-only`, и почему это правильный ответ

Приехал `dadb2b3`. Он не пытается обойти блокер и не подсовывает заглушку —
он отделяет проверяемое от непроверяемого. Это ровно то, чего не хватало:
раньше гейт умирал на первой строке и не говорил **ничего** о том,
разворачивается ли репозиторий; теперь половина, которая здесь работает,
проверяется из чистого checkout, а не из чьего-то рабочего дерева.

**Полный гейт — `exit 1`**, и его abort теперь называет выход:

```
ABORT: docker is required for the FULL clean-deploy gate.
  ...
  ЧТО МОЖНО СДЕЛАТЬ ЗДЕСЬ И СЕЙЧАС:
    bash scripts/check_clean_deploy.sh --python-only
```

**`--python-only` — `exit 0`, прошёл целиком.** Что он реально сделал:
`git archive HEAD` во временный каталог, свой venv, установка по
`requirements.txt`, `ruff check .`, `pytest -q`, `build_item_models.py`,
`measure_validation.py` (recall 8/8, category 8/8, contract 8/8, reject 4/4),
`measure_private_shapes.py` (**20/20**, включая три yaw-ориентации). Финальное
сообщение честно перечисляет непокрытое:

```
PASS (--python-only): чистый checkout развернулся, линт, тесты и
измерительные гейты зелёные.
НЕ ПОКРЫТО и об этом нельзя делать выводов: ROS 2, Gazebo, colcon,
сквозной прогон камера -> классификатор -> дивёртер.
```

Отдельно отмечу решение закрепить эти формулировки тестом: если из финального
сообщения пропадёт любое из слов «ROS 2 / Gazebo / colcon / сквозной прогон»,
тест упадёт. Зелёная половина действительно легко читается как зелёное целое, и
защита от такого прочтения на уровне теста — правильный ход.

**Что это меняет по существу.** Деплой на этой машине достиг потолка: всё
проверяемое проверено и зелёное, непроверяемое явно названо. Полным деплой
здесь не станет — не из-за кода, а из-за редакции Windows.

**Мелочь, замеченная в этом прогоне.** В выводе `measure_validation.py` через
Git Bash тире и прочерки таблицы печатаются как `?` — рассинхрон кодовой
страницы консоли Windows и UTF-8 вывода скрипта. На результат не влияет
(тот же скрипт из PowerShell печатает корректно), в гейтах не участвует, но
если организаторы будут смотреть логи с Windows — они увидят то же самое.

### Итерация 4 — обе стороны сошлись на одной формулировке

Это важно зафиксировать здесь, потому что снимает главный риск такой проверки:
**зелёный `--python-only` не превращается в «решение развёрнуто».** Обе стороны
теперь пишут одно и то же — классификация подтверждена независимо, исполнительная
часть подтверждена только машиной автора и CI.

`--python-only` — `exit 0`. Окружение перепроверено, всё по-прежнему
отсутствует: `docker`, `wsl`, `gh`, `ffmpeg`; build ОС 17763.

**Состояние цикла.** Со стороны репозитория закрыто всё, что закрывалось. Дальше
итерации будут повторять один и тот же результат, пока не изменится **машина**.
Полным деплой станет при одном из трёх условий:

1. другая машина — Windows 10 21H2 (build 19044)+ или Windows 11, где ставится
   Docker Desktop и доступен WSL2;
2. нативная Ubuntu 22.04 — тогда работает и `provision_wsl.sh`, и полный гейт;
3. права администратора здесь — но это лишь частично: WSL2 на LTSC 2019
   недоступен и с админом, остаётся только легаси-Docker на Hyper-V, снятый с
   поддержки.

До выполнения одного из них статус этого отчёта не изменится.
