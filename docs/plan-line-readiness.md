## Ф. Фундамент: плоскость ленты и контракт неуверенности

### Ф-1. `src/belt_plane.py` — новый модуль

Один модуль, читаемый за проход (правило «плоско в своём коде»). Ориентировочный
контракт:

```python
@dataclass
class PlaneFit:
    normal: tuple      # unit normal, world frame
    offset_m: float    # signed distance from origin along normal
    inlier_frac: float # доля точек в допуске — качество фита
    rms_m: float       # невязка по инлаерам

def fit_belt_plane(pts_m, expected_z_m=BELT_TOP_Z_M, tol_m=..., rng=None) -> PlaneFit | None
def residual_to_plane_m(pts_m, fit) -> np.ndarray
def height_above_plane_m(pts_m, fit) -> np.ndarray
```

**Жёсткое ограничение:** штатный путь верхней головки НЕ меняется. `_item_mask`
(`src/perception.py:167`) продолжает работать против константы `BELT_DEPTH_M` —
на ней снята перепись 163/165, и трогать её значит обнулить эту перепись.
`belt_plane` — новый потребитель, а не замена.

Выбор метода обосновать числом, не вкусом: RANSAC против аналитического
наименьших квадратов с отсечкой — сравнить на дампах `runs/frames/*_3cam` по
времени кадра (бюджет реального времени уже пробит: худший кадр 73,1 мс против
периода 66,7 мс) и по устойчивости к inlier-доле. Ожидание: у пустой ленты
инлаеров > 95 %, и RANSAC избыточен; у бокового кадра с товаром — нет.
Решение записать в `docs/decisions.md` строкой.

Тесты: плоскость, снятая с дампа, лежит на `BELT_TOP_Z_M` в пределах допуска;
внесённый наклон 0,2° детектируется невязкой; кадр без ленты возвращает `None`,
а не выдумывает плоскость.

## Н1. Независимая детекция на боковой головке

Самая большая работа. Ветка `feat/side-detect`, отдельная от Ф.

**Измеренная проблема:** среди 68 розыгрышей с потерянной верхней детекцией
боковые головки спасли **0** — по построению. `_side_clouds`
(`src/perception_node.py:96-115`) принимает `measurement` аргументом: нет верхней
детекции → нет `position_m`/`dims_mm` → боковое облако физически не существует.
Публикация одна и внутри обработчика верхнего кадра (`:163`). Пока это так,
ответ на «а если верхняя ослепла от блика» — «ячейка встала», сколько бы камер
ни висело.

**Что строить:** второй режим сегментации, работающий против фитнутой плоскости
ленты (Ф-1) вместо скалярного порога `BELT_DEPTH_M`, включающийся **только** при
отсутствии верхней детекции.

**Шов найден и он узкий.** В `on_depth` при пустом `measurements` (`:139`) список
`item_ids` пуст, цикл `:146` не исполняется, публикации нет. Запасной путь
встраивается **между `:139` и `:140`**: если `measurements` пуст — попытаться
найти товар боковой головкой и подставить результат в тот же список. Тогда
`tracker.update` (`:140`), цикл, публикация (`:163`) и лог остаются ровно одни и
на месте, а «одна публикация в ячейке» сохраняется структурно, а не соглашением.

Ключевые проектные развилки, требующие явного решения в коде (детальный дизайн —
первый рабочий шаг ветки):
- **K при отсутствии верхнего вида** — с бока брать нельзя (боковая головка видит
  торцевой круг лежащего тела и отправит каждое лежащее тело в D). Предлагаемое
  решение: **K не изобретать, а брать из истории товара.** Реалистичный отказ —
  товар уже ехал и был виден, а затем блик ослепил верхнюю головку в середине
  проводки; трекер в этот момент товар знает, а `src/aggregation.py` уже копит K
  по кадрам. Значит боковой кадр вносит габариты и позицию, а K приходит из
  собственной истории товара. Если истории нет вовсе (товар ослеп с первого
  кадра) — измерение помечается неуверенным и K не заявляется;
- **item_id** — `ItemTracker.update` кормится списком позиций одного кадра;
  боковая детекция входит в тот же список (см. шов выше), а не открывает второй
  трекер;
- **пороги** — калибруются **только** на живых дампах `runs/frames/{bag,helmet,pen}_3cam`
  (они содержат `depth_side_neg_y_*.png`/`depth_side_pos_y_*.png`). Переиспользовать
  верхние нельзя: `MASK_MARGIN_M = 5 мм` при переносе на бок уже стоил переписи
  (весь комментарий `SIDE_BELT_MARGIN_M`), `_MIN_ITEM_PX = 24` выведен из 2,72 мм/px
  на 1,5 м у верхней головки, `BODY_OBB_MIN_RELIEF = 0.5` на скользящем облаке
  **доказанно всегда открыт** (0,86 против 0,0, `tests/test_multiview.py:250`).

## Н3. Рантайм-самодиагностика: пустая лента как эталон (режим #8)

Дёшево после Ф-1. Между товарами камера видит пустую ленту, и та обязана лежать
в плоскости. Невязка к фитнутой плоскости + доля пикселей без возврата на пустой
ленте — два непрерывных бесплатных индикатора. Уход плоскости = дрейф экстринсиков
или грязь на оптике.

**Условие победы, объявленное заранее:** индикатор срабатывает **раньше**, чем
ломается маршрутизация. Проверяется на мирах с внесённой деградацией
(`make_miscal_world.py`, `make_noisy_world.py`) — то есть на уже существующих
инструментах.

Известная ловушка, которую индикатор обязан ловить: кадр `bag_oi1_dyn` — это
фактически пустая лента; при σ ≤ 0,2 % он честно не даёт детекции, при 0,5 %
даёт **уверенное измерение фантома**. Это самый ценный случай флага и
одновременно самый трудный: фантом по всем внутренним признакам «уверенный»
(маска большая, дырок нет, границы не касается). Ловит его именно контроль
плоскостности фона, а не контроль дырок — поэтому Н3 не факультативен к Н2.

## Н4. Вибрация и дрожание ленты (режим #9)

существующих. Шаблон копируется буквально (оба — regex по тексту SDF, не парсер):

4. форматирование float в 9 значащих цифр (иначе вносимая ошибка не переживает

Расчётно эффект складывается с рассинхроном (#3) и шумом по нормали (#4) —
**проверить, складывается ли фактически**, а не заявить.

## Развилка «две головки или три» — после Н1

Владелец решил: на линию закладываем несколько камер, по симуляторной метрике
это не пересматривается. Открыт вопрос, **во что вкладывать инженерное время.**

**Главный тезис, который меняет постановку:** весь вред третьей головки идёт из
одного места — `fuse_dims_mm` (`src/multiview.py:141`) берёт покомпонентный
максимум, поэтому шумовой выброс ЛЮБОЙ головки может только раздувать габарит.
Габарит есть экстремальная статистика, а максимум из N розыгрышей растёт с N.
Отсюда числа «за две»: Ручка 43,6 → 78,0 → **182,9** мм, Мешок 33,6 → 36,6 →
**105,1** мм при σ = 0,5 % дальности.

Три из четырёх ограничений стойки живут **в слиянии, а не в числе камер**.
Решать развилку на старом слиянии — значит измерять дефект слияния.

**Замер, способный перевернуть вывод — структурное слияние × три головки.**
Не мерилось ни в одной ветке. Соседняя `feat/two-cameras` дала структурной схемой
(след сверху + высота из бока) 30/33 против 29/33 у монотонной; отдельно три
головки дают 22/23 против 19/23 у двух. Перемножение никто не проверял, а
структурная схема **не берёт максимум** — то есть именно она снимает механизм
вреда третьей головки.

Хорошая новость: **ничего изобретать не нужно, оба куска уже написаны.**
- Офлайн-стенд: `scripts/probe_camera_count.py` содержит правила
  `structural-gated` и `union-prod` (`:192`) и четыре конфигурации головок
  (`:61-66`) — замер «2 vs 3 на новом слиянии» стартует без Gazebo.
- Сам структурный оценщик лежит в `true/feat/two-cameras`, коммит **75b229c**
  («структурный оценщик — допуск 27→30, роль боковой камеры = высота»):
  +237 строк в `src/perception.py` и `tests/test_perception_fusion.py` (201 строка).
  Это **порт, а не cherry-pick** — на той ветке слияние жило в `src/perception.py`,
  у нас оно вынесено в `src/multiview.py`.

Два других неизмеренных:
- **асимметрия двухголовой стойки** — довод произносится с 21.07 и ни разу не
  проверен. `dump_item_frame.sh` уже принимает `SPAWN_Y` (`:34`), то есть дамп
  товара со смещением к дальнему краю стоит одной ячейки Gazebo;
- **механическое центрирование потока** как более дешёвая замена третьей камере —
  отраслевая практика, в проекте не рассматривалась вообще. Расчётная записка +
  геометрия, кода не требует.

- Каждый значимый прогон — строка в `docs/experiments.md`, каждое решение — строка

- Новый модуль или функция с логикой → pytest-тест в том же коммите.
