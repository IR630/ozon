# Промпт: детальный план на первые 3 дня

> Запускать в новой сессии Claude Code в корне проекта, в plan mode (Shift+Tab).
> Перед запуском заполнить блок «Вводные» ниже.

---

Составь детальный план работ на первые 3 дня хакатона для команды из 5 senior-разработчиков.

## Контекст (прочитай перед планированием)

- `PLAN.md` — стратегия, этапы и рабочие потоки команды (план строится строго по ним)
- `docs/md/task.md` — постановка задачи (трек 3: роботизированная сортировка)
- `docs/md/criteries.md` — критерии оценки и баллы (приоритеты плана — по баллам)
- `docs/md/plan.md` — геометрия участка 6×10 м, фиксированные точки A/B, свободные C/D
- `docs/md/models.md` — анализ 11 тестовых STL-моделей и карта пограничных случаев
- `docs/md/software.md` — разрешённое ПО (выходить за список нельзя)
- `scripts/analyze_models.py` + `tests/` — готовая база: правила классификации по STL с тестами

## Вводные (заполнить перед запуском)

- Даты хакатона и дедлайн сдачи: <...>
- Занятость команды в первые 3 дня (фуллтайм / вечера): <...>
- Доступное железо (GPU для обучения/рендера, если есть): <...>
- Выбран ли уже симулятор (PyBullet vs Gazebo+ROS 2) или выбор — задача дня 1: <...>

## Требования к плану

1. Горизонт — 3 дня, разбивка по полудням. День 1 обязан закончиться сквозным
   скелетом (этап 1 из PLAN.md): один товар проходит путь от появления на виртуальной
   ленте до физического попадания в зону B/C/D.
2. Для каждого из 5 потоков (cv / cls / sim / int / docs — см. PLAN.md) на каждые
   полдня: задача, ожидаемый артефакт (файл/скрипт/результат в репозитории),
   проверяемый критерий готовности («работает X, запускается командой Y»).
3. Явно выдели зависимости между потоками и точки синхронизации команды
   (что должно быть готово, чтобы другой поток не простаивал). Первая точка —
   контракт сообщений CV → контроллер: его формат согласуется в первые часы.
4. Решения, которые нужно принять в день 1, оформи отдельным списком с вариантами
   и рекомендацией (как минимум: симулятор, механизм перекладки, формат контракта).
5. Риски первых 3 дней и план Б для каждого (например: физика нестабильна
   в выбранном симуляторе, синтетический датасет не переносится, механизм
   не успевает за тактом ленты 1 м/с).
6. Учитывай распределение баллов: исполнительная часть + интеграция +
   производительность (65) важнее классификации (20). План не должен позволять
   команде трое суток полировать CV.
7. Каждый день заканчивается: зелёные тесты, коммиты по GIT.md, одна строка
   в docs/experiments.md о достигнутом состоянии.

## Формат результата

Файл `PLAN-3DAYS.md` в корне: таблица «день/полдень × поток», список решений дня 1,
зависимости, риски. Без воды — план, по которому завтра утром можно начать работать.
