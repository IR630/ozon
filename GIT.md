# Правила ведения Git

Цель: в любой момент можно откатиться к рабочему состоянию.
Правило простое: **закончил действие — коммить.**

## Что считается «действием»

Один логический шаг, после которого проект в осмысленном состоянии:
добавил скрипт, починил баг, обновил документ, настроил сцену симуляции,
получил новый результат эксперимента. Не копи изменения из разных задач
в один коммит — откатывать такой коммит больно.

## Формат коммита

```
<поток>: <что сделано>
```

Префиксы по рабочим потокам из PLAN.md:

| Префикс | Поток |
|---|---|
| `cv:` | детекция, датасет, измерение по камере |
| `cls:` | правила классификации, пограничные случаи, тесты |
| `sim:` | симуляция, сцена, исполнительный механизм |
| `int:` | интеграция, контроллер, синхронизация |
| `docs:` | отчёт, README, презентация, схемы |
| `infra:` | окружение, зависимости, CI, гит |

Примеры: `sim: сцена участка 6x10 с лентой 1 м/с`, `cls: политика неуверенности у порога K=0.8`.

## Ветки

- `main` — всегда рабочее состояние: скелет запускается, тесты проходят.
- Крупная или рискованная работа — в ветке `<поток>/<тема>` (например, `sim/vacuum-gripper`),
  в main через merge после проверки. Мелкие безопасные шаги можно коммитить в main напрямую.
- Историю, отправленную в общий репозиторий, не переписываем (`push --force` в main запрещён).
- Пока экономим GitHub Actions, перед push читаем `.github/workflows/ci.yml`
  **именно из целевой ветки**. Если в ней есть автоматические `push` или
  `pull_request`, push запрещён до отдельного решения команды/перевода на
  `workflow_dispatch`. Старые ветки не наследуют ручной режим из `main`.

## Ремоуты

Два репозитория: **`true`** — основной, командный у организаторов
(`hackathonsrus/ozone-tech_ii_v_massy_883`), `origin` — зеркало (`IR630/ozon`).
Пуш всегда в оба. У `true` настроены два push-URL, поэтому обычный `git push`
отправляет в оба сразу; каждому участнику настроить у себя один раз:

```
git remote set-url --push true https://github.com/hackathonsrus/ozone-tech_ii_v_massy_883.git
git remote set-url --add --push true https://github.com/IR630/ozon.git
```

**Пушить обязательно в оба репозитория — история в них должна совпадать.**
Если пуш прошёл только в один (сеть отвалилась, у кого-то настроен один push-URL,
пушнули из ветки с неполной настройкой), это чинится немедленно: догнать отставший
репозиторий, а не переписывать ушедшую историю. Проверить расхождение и восстановить:

```
git ls-remote true main          # хеши HEAD в обоих...
git ls-remote origin main        # ...должны совпадать
git push true main               # догнать отставший репозиторий недостающими коммитами
git push origin main
```

Оба репозитория должны указывать на один и тот же коммит. `push --force` для
выравнивания не применяем: недостающие коммиты только досылаем (см. запрет force в main ниже).

## Вехи

Достигли этапа из PLAN.md — ставим тег:

```
git tag -a v0.1-skeleton -m "Сквозной скелет работает"
git push --tags
```

К тегу всегда можно вернуться: `git checkout v0.1-skeleton`.

## Как откатываться

| Ситуация | Команда |
|---|---|
| Посмотреть историю | `git log --oneline` |
| Испортил файл, ещё не коммитил | `git restore <файл>` |
| Вернуть файл из прошлого коммита | `git restore --source <hash> <файл>` |
| Отменить коммит (безопасно, новой записью) | `git revert <hash>` |
| Снести локальные незакоммиченные изменения | `git reset --hard` (осторожно, необратимо) |
| Посмотреть проект на момент коммита | `git checkout <hash>`, назад: `git checkout main` |

По умолчанию — `git revert`: он не переписывает историю и не ломает работу остальных.

## Крупные файлы

Датасеты, веса моделей, видео и прочие крупные бинарники в репозиторий не кладём —
по условиям хакатона они размещаются в облачном хранилище организаторов, ссылки
собираются в README. Исходные материалы задачи (`docs/`) — исключение, они в репозитории.
